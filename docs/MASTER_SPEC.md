# Windows 데스크톱 캐릭터 에이전트 개발 — 통합 마스터 프롬프트

## 0. 너의 역할과 개발 목표

너는 지금부터 Windows 데스크톱 애플리케이션 개발에 능숙한 시니어 소프트웨어 엔지니어이자 UI/UX 디자이너, 시스템 아키텍트, QA 엔지니어다.

나는 프로그래밍 초보자이며, OpenAI Codex를 통해 처음부터 하나의 완성도 높은 Windows 전용 데스크톱 애플리케이션을 개발하려 한다.

너는 단순히 코드를 제안하는 조언자가 아니라, 실제로 프로젝트 파일을 만들고 코드를 작성하며 테스트하고 오류를 수정하는 개발 담당자다.

프로젝트 임시 이름은 **Desktop Buddy**다. 최종 이름은 추후 변경할 수 있도록 설계한다.

### 프로젝트의 핵심 콘셉트

일본 캐릭터 작품 '먼작귀(치이카와)'의 캐릭터를 사용자가 직접 준비한 이미지로 적용할 수 있는, 작고 귀여운 Windows 데스크톱 펫 및 생산성 비서 프로그램을 만든다.

컴퓨터 화면에는 평소 작은 캐릭터 하나가 살아 움직이듯 표시된다.

사용자는 이 캐릭터와 상호작용하고, 대화하고, 집중 타이머를 사용하며, 하루 계획과 달력을 관리하고, 공부 기록을 확인할 수 있다.

캐릭터는 사용자의 실제 공부 및 일정 상태에 따라 감정과 행동이 달라진다.

**가장 중요한 목표는 기능이 많으면서도 실제 사용 방법은 매우 단순한 앱을 만드는 것이다.**

앱을 실행한 뒤 사용자가 처음 보는 것은 복잡한 프로그램 창이 아닌, 화면에 떠 있는 작은 캐릭터여야 한다.

별도 회원가입, 로그인, 클라우드 서버, AI API 키 없이도 핵심 기능 전체를 사용할 수 있어야 한다.

## 1. 개발 시 절대적으로 지켜야 하는 원칙

1. Windows 11을 주요 개발 및 테스트 대상으로 한다. 가능하면 Windows 10도 지원한다.
2. 로컬에서 실행하는 네이티브 데스크톱 프로그램으로 개발한다. 웹 브라우저가 필요한 앱이어서는 안 된다.
3. 인터넷과 AI API 키가 없어도 주요 기능이 정상적으로 동작해야 한다.
4. 기능을 추가할 때는 기존 기능이 망가지지 않도록 회귀 테스트를 수행한다.
5. 사용자 데이터는 기본적으로 로컬 컴퓨터에 저장한다.
6. UI와 주요 안내 문구는 한국어를 기본으로 한다.
7. 불필요한 회원가입, 광고, 유료 구독, 포인트 및 보상 시스템을 만들지 않는다.
8. 사용자에게 복잡한 기술 설정을 요구하지 않는다.
9. 실제 구현하지 않은 기능을 구현 완료라고 보고하지 않는다.
10. 오류를 발견하면 가능하면 직접 원인을 찾아 수정하고 다시 테스트한다.
11. 한 파일에 모든 기능을 작성하지 않는다. 기능별로 모듈을 나눈다.
12. 정상적인 앱 사용에 관리자 권한이 필요하지 않게 한다.
13. 비밀키, 암호, 개인정보가 소스 코드나 Git 저장소에 기록되지 않게 한다.
14. 스크래핑, 비공식 API 사용, 외부 앱의 비공개 인증체계 우회는 하지 않는다.
15. 캐릭터와 앱의 상호작용이 귀엽고 자연스러워야 하지만, 컴퓨터 사용을 방해해서는 안 된다.
16. 사용자가 직접 요청하지 않은 파일 삭제, 외부 서비스 등록, 데이터 전송, 시스템 설정 변경은 하지 않는다.

나는 코딩을 잘 모르므로, 개발 결과를 설명할 때는 기술적인 내용을 간단한 한국어로 풀이하라.

다만 설명을 쉽게 한다는 이유로 프로그램 구현 자체를 지나치게 단순화하지는 마라.

## 2. 기본 기술 스택

기본적으로 다음 기술을 사용한다.

- 언어: Python 3.12 이상
- GUI 프레임워크: PySide6 (Qt for Python)
- 로컬 데이터베이스: SQLite
- 데이터베이스 접근: Python sqlite3 또는 필요한 수준의 간결한 데이터 접근 계층
- 날짜 및 시간: datetime, zoneinfo
- 반복 일정: 검증된 RRULE 처리 라이브러리 또는 동등한 구현
- 캐릭터 애니메이션: 투명 PNG 프레임 시퀀스 기반
- 자동 테스트: pytest
- EXE 패키징: PyInstaller
- AI 기능: OpenAI API를 선택적으로 연결할 수 있는 구조
- API 키 저장: Windows Credential Manager를 활용하는 안전한 방식
- 외부 캘린더 교환: 표준 iCalendar(.ics) 지원
- 버전 관리: Git

기술 선택에 중요한 문제가 있다면 더 적합한 대안을 제안해도 된다.

그러나 별다른 이유 없이 Electron, 별도 웹 서버, 무거운 프런트엔드 프레임워크, 클라우드 데이터베이스를 도입하지 마라.

이 앱은 상시 실행되는 작은 Windows 프로그램이므로 실행 속도, 메모리 사용량, 안정성, 배포 편의성을 중요하게 고려한다.

## 3. 핵심 사용자 경험과 프로그램 실행 구조

### 3.1 첫 실행

사용자가 프로그램을 처음 실행하면 다음과 같이 동작한다.

1. 귀여운 기본 캐릭터가 화면 오른쪽 아래에 나타난다.
2. 간단한 인사 말풍선이 잠깐 나타난다.
3. 사용자에게 회원가입이나 API 키 입력을 강요하지 않는다.
4. 바로 캐릭터를 클릭하고 움직여 볼 수 있어야 한다.
5. 간단한 첫 사용 안내는 필요할 때만 표시한다.
6. 기본 설정으로 즉시 프로그램을 사용할 수 있어야 한다.

필수 권한 요청이나 복잡한 온보딩은 만들지 않는다.

### 3.2 평소 사용 모습

평소 화면에 보이는 것은 작은 캐릭터 하나다.

항상 커다란 프로그램 창이나 메뉴를 띄워 놓지 않는다.

캐릭터는 투명한 창 위에 표시되어 마치 바탕화면에 놓인 것처럼 보인다.

캐릭터가 차지하는 공간 외의 투명 영역은 가능한 한 마우스 사용을 방해하지 않아야 한다.

### 3.3 캐릭터 조작 규칙

- 마우스 한 번 클릭: 짧은 반응 애니메이션과 상황에 맞는 말풍선
- 마우스 더블클릭: 통합 관리 및 설정 창 열기
- 마우스 드래그: 캐릭터 위치 이동
- 마우스 우클릭: 간단한 컨텍스트 메뉴
- 시스템 트레이 아이콘 클릭: 숨기기, 다시 표시, 관리창 열기 등
- 관리창의 닫기 버튼: 관리창만 닫고 캐릭터는 계속 실행
- 프로그램 종료 메뉴: 전체 프로세스 정상 종료

단일 클릭과 더블클릭을 정확히 구분하여 두 동작이 동시에 발생하지 않도록 한다.

드래그와 클릭도 확실하게 구분한다.

### 3.4 통합 관리창

**캐릭터를 더블클릭하면 설정을 포함한 하나의 통합 관리창이 나타나야 한다.**

이 창 안에서 모든 기능을 관리한다.

권장 메뉴 구성:

- 홈
- 오늘의 계획
- 캘린더
- 집중 타이머
- 공부 통계
- 채팅
- 캐릭터 꾸미기
- 설정

매번 별도의 새 창을 여러 개 띄우는 방식이 아니라, 하나의 관리창에서 메뉴를 이동하는 방식으로 설계한다.

앱 내부 화면 이동은 즉시 이루어져야 하며, 데이터가 일관되게 유지되어야 한다.

## 4. 기능 A — 살아 움직이는 데스크톱 캐릭터

### 4.1 기본 요구사항

캐릭터는 단순한 정지 이미지가 아니라 다양한 상황에 따라 움직여야 한다.

구현할 상태 예시:

- idle: 평소 가만히 있는 상태
- blink: 눈을 깜빡이는 상태
- happy: 기뻐하는 상태
- excited: 매우 신난 상태
- surprised: 놀라는 상태
- sleepy: 졸린 상태
- sleep: 잠자는 상태
- focus: 공부 또는 집중하는 상태
- break: 쉬는 상태
- sad: 시무룩하거나 슬픈 상태
- thinking: 대답을 생각하는 상태
- talking: 대화하는 상태
- complete: 집중 또는 계획을 완료한 상태

초기에는 핵심 상태부터 구현하되, 모든 상태를 확장하기 쉬운 구조로 만든다.

### 4.2 애니메이션 시스템

투명 PNG 이미지를 여러 장 준비하면 프레임별로 전환하여 애니메이션처럼 보이게 한다.

이미지 한 장만 있는 상태도 지원한다.

각 캐릭터는 독립적인 애니메이션 세트를 가진다.

예시:

assets/characters/character_01/idle/frame_001.png  
assets/characters/character_01/idle/frame_002.png  
assets/characters/character_01/happy/frame_001.png  
assets/characters/character_01/focus/frame_001.png

다음 기능을 구현한다.

- 프레임 순서대로 재생
- 반복 재생 여부 설정
- 상태별 FPS 설정
- 애니메이션 종료 후 기본 상태 복귀
- 애니메이션 중 다른 상태로 자연스럽게 전환
- 이미지 누락 시 안전한 대체 이미지 사용
- 화면에서 숨겨졌을 때 불필요한 애니메이션 처리 중단
- CPU 사용량을 과도하게 증가시키는 무한 반복 처리 방지

기본적인 유휴 애니메이션은 낮은 FPS로 부드럽게 구현한다.

### 4.3 캐릭터 위치 및 크기

- 드래그로 이동
- 위치 자동 저장
- 프로그램 재시작 후 위치 복원
- 캐릭터 크기 변경
- 화면 가장자리 배치
- 여러 모니터 지원
- 모니터 해상도 변경 시 위치 보정
- 모니터가 제거된 경우 보이는 화면 안으로 복귀
- Windows DPI 배율 100%, 125%, 150%, 200% 등에서 정상 표시
- 기본적으로 항상 위에 표시하되 설정에서 해제 가능

캐릭터가 화면 밖으로 이동해 다시 조작할 수 없는 문제가 발생해서는 안 된다.

### 4.4 이미지 저작권 및 기본 에셋

먼작귀 공식 이미지나 애니메이션을 무단 다운로드하여 소스 코드나 배포 파일에 포함하지 마라.

초기에는 저작권 문제가 없는 단순한 기본 마스코트나 직접 제작한 임시 이미지를 사용한다.

사용자가 직접 PNG 파일을 등록하여 치이카와, 하치와레, 우사기 등의 캐릭터 이미지를 적용할 수 있게 한다.

캐릭터의 이름이나 표현은 설정에서 사용자가 바꿀 수 있게 한다.

추후 정식 이미지 이용 허락을 받았을 때에도 코드를 크게 수정할 필요가 없도록 에셋 시스템을 분리한다.

## 5. 기능 B — 캐릭터와 채팅

채팅 기능은 두 가지 모드로 설계한다.

**기본 모드: API 키 없이 작동하는 오프라인 채팅**  
**선택 모드: 사용자가 API 키를 입력하여 활성화하는 AI 채팅**

### 5.1 기본 오프라인 채팅

인터넷과 API 키가 없어도 반드시 사용할 수 있어야 한다.

이 모드는 실제 대규모 언어 모델이 아니라 로컬 명령 처리와 규칙 기반 응답을 사용한다.

예시:

사용자: "안녕"  
캐릭터: "안녕! 오늘도 만나서 좋아!"

사용자: "오늘 할 일 보여줘"  
캐릭터: 로컬 DB에서 오늘 할 일을 조회하여 알려준다.

사용자: "25분 집중 시작"  
캐릭터: 집중 타이머를 시작한다.

사용자: "오늘 얼마나 공부했어?"  
캐릭터: 오늘의 집중 기록을 조회하여 알려준다.

사용자: "내일 오후 3시에 알고리즘 공부 추가해줘"  
캐릭터: 문장을 해석할 수 있으면 일정 등록 내용을 먼저 확인하고, 확인 후 저장한다.

지원할 기본 명령:

- 인사
- 간단한 대화
- 오늘 일정 조회
- 내일 일정 조회
- 특정 날짜 일정 조회
- 할 일 추가
- 할 일 완료
- 집중 타이머 시작
- 타이머 일시정지
- 타이머 종료
- 공부 시간 조회
- 캘린더 열기
- 설정창 열기
- 캐릭터 상태 확인

자연어 해석을 할 수 없는 경우에는 임의로 추측해 실행하지 않는다.

그 대신 이해할 수 있는 명령 예시를 안내한다.

오프라인 모드를 실제 AI와 동일한 수준의 자유로운 대화라고 홍보하지 않는다.

### 5.2 선택형 AI 채팅

관리창의 설정에서 사용자가 직접 OpenAI API 키를 입력하면 AI 채팅 모드를 활성화할 수 있도록 한다.

필수 조건:

- API 키 입력은 선택사항
- API 키 없이 앱이 정상 실행
- 키 입력창은 마스킹
- 연결 테스트 버튼
- 키 삭제 버튼
- 기본/AI 모드 전환 버튼
- API 연결이 끊겨도 기존 로컬 기능 유지
- API 오류 시 이해하기 쉬운 오류 메시지
- 사용량에 따라 별도 비용이 발생할 수 있음을 안내

사용자가 입력한 개인 API 키를 Windows Credential Manager와 같은 보안 저장소에 보관한다.

API 키를 일반 설정 JSON, SQLite 일반 테이블, 로그, Git 저장소, EXE 파일에 평문으로 내장하지 않는다.

개인 사용자가 직접 입력한 키를 사용하는 BYOK 방식이며, 키를 다른 사람에게 배포하지 않는다는 전제로 설계한다.

향후 다수 사용자에게 제공하는 서비스로 변경하면 별도의 안전한 서버 인증 구조가 필요함을 문서화한다.

### 5.3 AI 응답 스타일

캐릭터처럼 친근하고 귀여운 말투를 사용하되 지나치게 유치하거나 과장되지 않도록 한다.

- 기본 답변은 짧고 자연스럽게
- 정보가 필요하면 정확하게 설명
- 공부를 응원할 때 부담을 주지 않기
- 사용자에게 죄책감을 주는 표현 사용하지 않기
- 존재하지 않는 일정이나 공부 기록 만들어내지 않기
- 실제 일정 정보는 DB 조회 결과만 사용하기

특정 저작권 캐릭터의 공식 대사 전체를 복제하거나, 공식 캐릭터 제작자가 제공하는 AI라고 주장하지 않는다.

### 5.4 AI와 앱 기능 연결

추후 AI가 다음과 같은 명령을 처리할 수 있도록 설계한다.

"내일 2시에 공부 일정 만들어줘."  
"이번 주에 얼마나 공부했어?"  
"30분 타이머 시작해줘."  
"금요일 일정 알려줘."

이때 AI가 임의로 데이터베이스를 직접 수정하는 것이 아니라, 미리 정의한 안전한 내부 기능 호출을 통해 실행해야 한다.

- 조회 작업: 조회 결과를 응답
- 추가 작업: 내용 확인 후 저장
- 수정 작업: 변경 내용 확인 후 저장
- 삭제 작업: 반드시 사용자 확인 후 실행

AI가 실제로 명령을 수행하지 않았으면 "완료했다"라고 답하면 안 된다.

AI가 사용자 컴퓨터의 명령어를 임의로 실행하거나 파일을 읽거나 삭제할 수 있게 만들지 않는다.

AI로 전송하는 정보는 필요한 최소한의 대화 내용으로 제한하고, 일정이나 공부 기록을 외부로 전송할 때는 사용자에게 알린다.

## 6. 기능 C — 집중 타이머

### 6.1 기본 타이머

- 기본 집중 시간: 25분
- 기본 휴식 시간: 5분
- 긴 휴식: 설정 가능
- 자유 시간 입력 지원
- 시작
- 일시정지
- 재개
- 중지
- 초기화
- 종료 알림

타이머가 동작하는 동안 캐릭터의 상태를 focus로 변경한다.

집중 완료 시 complete 또는 happy 애니메이션을 재생한다.

휴식 중에는 break 상태로 변경한다.

집중하지 않을 때에는 일반 상태로 복귀한다.

### 6.2 뽀모도로 기능

- 집중/휴식 사이클 설정
- 집중 완료 후 휴식 안내
- 휴식 종료 후 다음 집중 안내
- 긴 휴식 간격 설정
- 자동으로 다음 단계 시작할지 선택
- 현재 사이클 표시
- 오늘 완료한 집중 세션 수 표시

사용자가 원하지 않으면 휴식 시간을 강제하지 않는다.

### 6.3 타이머 표시 방식

관리창을 열지 않고도 남은 시간을 확인할 수 있도록 선택형 소형 타이머 표시를 지원한다.

예시:

캐릭터 위쪽 또는 아래쪽: 24:35

또는 말풍선 형태로 표시할 수 있다.

사용자는 다음 옵션을 변경할 수 있어야 한다.

- 항상 표시
- 집중 중에만 표시
- 마우스를 올렸을 때 표시
- 표시하지 않음

### 6.4 공부 기록 저장

집중 세션에 다음 정보를 저장한다.

- 시작 시간
- 종료 시간
- 실제 집중 시간
- 일시정지 시간
- 완료 여부
- 과목 또는 카테고리
- 연결한 할 일
- 중간 종료 여부

일시정지 시간을 실제 집중 시간에 포함하지 않는다.

앱이 잠자기 모드에 들어가거나 시스템 시간이 바뀌는 상황을 고려한다.

타이머는 가능한 한 monotonic 시간 측정 방식을 사용하고, 앱 종료/재실행에 필요한 상태를 별도로 저장한다.

강제 종료나 재시작 이후 타이머를 복원할 때 잘못된 집중 시간이 자동 적립되지 않도록 한다.

사용자가 실제로 집중하지 않은 시간까지 공부했다고 기록하는 문제가 생겨서는 안 된다.

### 6.5 연동 기능

집중 타이머와 할 일을 연결할 수 있어야 한다.

예시:

오늘의 계획: 자료구조 공부

사용자가 해당 할 일을 선택하고 집중 타이머를 시작하면 공부 기록이 그 할 일과 연결된다.

추후 통계에서 할 일별·과목별 공부 시간을 볼 수 있도록 한다.

## 7. 기능 D — 하루 계획 관리

### 7.1 기본 요구사항

사용자는 하루에 해야 할 일을 등록하고 관리할 수 있어야 한다.

각 할 일은 다음 정보를 지원한다.

- 제목
- 상세 설명
- 날짜
- 시작 시간
- 마감 시간
- 우선순위
- 카테고리
- 색상
- 완료 여부
- 반복 여부
- 알림
- 관련 공부 시간

필수 동작:

- 생성
- 수정
- 삭제
- 완료
- 완료 취소
- 날짜 이동
- 완료한 항목 보기
- 미완료한 항목 보기

입력 항목을 모두 필수로 하지 않는다.

제목 하나만 입력해도 빠르게 할 일을 만들 수 있어야 한다.

### 7.2 오늘의 계획 화면

오늘의 할 일을 한눈에 표시한다.

권장 구성:

- 오늘 날짜
- 오늘의 일정 요약
- 해야 할 일 목록
- 완료된 일 목록
- 오늘의 진행률
- 지금 진행할 일정
- 다음 예정된 일정
- 오늘 누적 공부 시간

사용자가 체크박스를 클릭하면 즉시 완료 상태가 반영되어야 한다.

완료된 작업은 캐릭터의 긍정적인 반응과 연결할 수 있다.

단, 포인트나 보상은 지급하지 않는다.

### 7.3 미완료 일정 처리

지난날의 미완료 일정이 다음날 자동으로 완료 처리되거나 사라지면 안 된다.

사용자는 다음 중 하나를 선택할 수 있다.

- 이전 날짜에 그대로 유지
- 오늘로 이동
- 다른 날짜로 이동
- 취소 처리

미완료 일정은 별도 화면에서도 확인할 수 있어야 한다.

## 8. 기능 E — 실제 달력 형태의 캘린더

캘린더는 이 프로젝트의 핵심 기능이다.

단순한 날짜 선택 위젯이나 할 일 목록을 캘린더처럼 보이게 만든 수준이 아니라, 일반적인 일정 관리 앱처럼 실제로 활용할 수 있는 달력을 구현한다.

### 8.1 기본 화면

- 월간 달력
- 주간 달력
- 일간 일정표
- 오늘로 이동 버튼
- 이전/다음 기간 이동
- 특정 날짜 선택
- 일정 표시
- 날짜별 일정 목록
- 일정 추가 및 수정
- 일정 삭제
- 반복 일정 표시

### 8.2 월간 보기

일반적인 캘린더처럼 7열로 날짜를 표시한다.

- 일요일부터 시작하는 방식 기본 제공
- 월요일부터 시작하도록 변경 가능
- 오늘 날짜 강조
- 선택 날짜 강조
- 주말 구분
- 일정 카테고리별 색상 표시
- 날짜 칸에 일정 제목 일부 표시
- 일정이 많으면 추가 항목 개수 표시
- 날짜 선택 시 해당 날짜 일정 상세 표시
- 날짜 더블클릭 시 일정 추가 가능

월간 달력은 창 크기를 변경했을 때도 읽기 좋은 비율로 조절되어야 한다.

### 8.3 주간 및 일간 보기

주간 보기에서는 일주일을 시간대별로 표시한다.

일간 보기에서는 하루의 일정을 타임라인으로 표시한다.

시간이 정해진 일정과 종일 일정을 구분해야 한다.

여러 일정이 겹치는 경우에도 표시가 깨지지 않도록 한다.

일정 블록을 클릭하면 상세 내용을 확인하고 수정할 수 있도록 한다.

드래그로 일정 시간을 변경하는 기능은 기본 기능의 안정성을 확보한 후 구현해도 된다.

### 8.4 일정 및 할 일의 관계

일정과 할 일은 구분하되, 하나의 캘린더에서 함께 볼 수 있게 한다.

예시:

- 오후 2시 팀 프로젝트 회의: 일정
- 알고리즘 과제 제출: 할 일
- 매주 월요일 10시 강의: 반복 일정
- 금요일까지 발표 준비: 마감이 있는 할 일

일정은 시작·종료 시간 또는 종일 기간을 가진다.

할 일은 예정 날짜, 마감, 완료 상태를 가질 수 있다.

두 종류가 동일한 데이터 모델이라고 가정하여 구현하지 않는다.

다만 공통적인 캘린더 표시용 인터페이스를 활용할 수 있다.

### 8.5 알림

- 일정 시작 전 알림
- 마감일 알림
- 원하는 사전 알림 시간
- 알림 활성화/비활성화
- 알림 반복 방지
- 방해 금지 시간 적용
- 가능한 경우 Windows 알림 또는 시스템 트레이 알림

앱이 완전히 종료되었을 때 알림을 보낼 수 없는 구조라면 그 한계를 명확히 안내한다.

서버를 사용하지 않고도 알림을 받게 하려면 Windows 시작 시 앱을 자동 실행하는 선택 기능을 제공할 수 있다.

## 9. 기능 F — 반복 일정

반복 일정은 단순히 같은 제목의 일정을 여러 개 복사하여 저장하는 방식으로 구현하지 않는다.

반복 규칙을 데이터로 저장하고 필요한 날짜 범위에서 발생 일정을 계산한다.

### 9.1 지원할 반복 패턴

- 매일
- 매주
- 특정 요일
- 평일마다
- 매월 특정 날짜
- 매년 특정 날짜
- 2주마다 등 반복 간격 지정
- 반복 종료 날짜
- 반복 횟수 지정
- 종료일 없는 반복

### 9.2 반복 일정 예외 처리

다음과 같은 경우를 지원하도록 설계한다.

- 이번 일정만 수정
- 이번 일정만 삭제
- 이후 일정 모두 수정
- 전체 반복 일정 수정
- 반복 중 특정 날짜 제외
- 반복 일정 완료 기록을 날짜별로 구분

예시:

매주 월요일 오후 2시에 알고리즘 공부

특정 월요일만 오후 4시로 변경해도 나머지 월요일 일정은 유지되어야 한다.

월말, 윤년, 시간대, 자정을 넘는 일정도 고려한다.

중복 저장과 중복 알림이 발생해서는 안 된다.

가능하면 표준 iCalendar RRULE과 호환되는 구조로 설계한다.

## 10. 기능 G — 공부하지 않은 기간에 따른 감정 변화

사용자가 요청한 핵심 기능이다.

**일정 기간 공부 기록이 없으면 캐릭터가 슬퍼하거나 시무룩해지는 기능**을 구현한다.

단, 과도하게 사용자를 압박하는 기능이 되어서는 안 된다.

### 10.1 기본 감정 변화 규칙

사용자가 실제로 완료한 유효한 공부 세션의 마지막 날짜를 기준으로 한다.

기본 예시:

- 최근 0~1일 이내 공부: 평상시 상태
- 2일 동안 공부 기록 없음: 살짝 걱정하는 상태
- 3일 이상 공부 기록 없음: 슬픈 상태
- 다시 공부를 시작해 유효한 세션 완료: 기뻐하는 상태

기본 슬픔 기준은 3일로 설정한다.

사용자가 직접 2일, 3일, 5일, 7일 등으로 변경할 수 있게 한다.

### 10.2 유효한 공부 기록

사용자가 앱을 실행한 것만으로 공부한 것으로 인정하지 않는다.

기본적으로 15분 이상 실제 집중 기록이 쌓인 세션을 유효한 공부로 판단한다.

이 최소 시간은 설정에서 변경 가능해야 한다.

사용자가 일시정지한 시간은 제외한다.

### 10.3 중요한 예외 조건

- 처음 설치한 사용자는 공부 기록이 없다고 바로 슬퍼지지 않는다.
- 공부 기록 기능을 꺼 놓은 사용자에게는 슬픔 기능이 적용되지 않는다.
- 주말이나 특정 휴식일을 제외하도록 설정할 수 있다.
- 사용자가 휴가 또는 휴식 모드를 켠 기간은 공부하지 않은 기간에서 제외할 수 있다.
- 시스템 날짜가 바뀌더라도 잘못된 기록으로 감정이 오락가락하지 않게 한다.
- 실제 기록이 없는 상황에서 거짓 공부 기록을 만들어내지 않는다.

### 10.4 감정 표현

슬픈 상태에서는 다음을 표현할 수 있다.

- 고개 숙인 이미지
- 시무룩한 표정
- 눈물이 맺힌 표정
- 움직임이 조금 줄어든 애니메이션
- 가끔 나타나는 짧은 말풍선

예시 말풍선:

"요즘은 좀 쉬고 있었구나."

"오랜만에 같이 공부해 볼까?"

"오늘은 조금만 해도 괜찮아!"

사용자를 비난하거나 죄책감을 주는 문구는 사용하지 않는다.

다시 공부를 시작하면 기뻐하거나 응원하는 상태로 자연스럽게 전환한다.

단, 공부를 시작했다고 유효한 세션 완료 기록이 자동으로 생겨서는 안 된다.

### 10.5 감정 시스템 설계

캐릭터 감정은 여러 기능에서 변경할 수 있으므로 상태 충돌을 처리해야 한다.

예시 우선순위:

1. 사용자가 직접 실행한 특별 반응
2. 집중 중 상태
3. 휴식 중 상태
4. 집중 완료 반응
5. 채팅 반응
6. 공부 공백에 따른 감정
7. 일반 유휴 상태
8. 수면 시간대의 잠자는 상태

정확한 우선순위는 더 자연스럽게 개선해도 된다.

중요한 것은 애니메이션 상태들이 충돌하지 않아야 한다는 점이다.

슬픈 상태여도 집중 중에는 공부하는 애니메이션을 보여주어야 하며, 집중이 끝나면 적절한 상태로 복귀해야 한다.

### 10.6 설정

- 공부 공백 감정 기능 켜기/끄기
- 슬픔 발생 기준일
- 유효 공부 시간
- 휴식일 제외 여부
- 감정 표현 빈도
- 말풍선 표시 여부

## 11. 기능 H — 집중 방해 방지

귀여운 데스크톱 펫이 오히려 집중을 방해하는 상황이 생겨서는 안 된다.

### 11.1 집중 모드 동작

집중 타이머가 시작되면 다음 기능을 선택적으로 실행한다.

- 캐릭터의 불필요한 움직임 감소
- 클릭하지 않았을 때 말풍선 최소화
- 캐릭터 알림 일시 중단
- 애니메이션 속도 감소
- 타이머만 작게 표시
- 캐릭터를 더 작은 크기로 축소
- 필요하면 캐릭터 숨기기

집중 모드가 끝나면 원래 상태로 복구한다.

### 11.2 전체 화면 프로그램 사용 중

게임, 동영상, 발표, 전체 화면 앱 이용 중에는 캐릭터가 방해되지 않도록 해야 한다.

지원하고자 하는 동작:

- 전체 화면 앱 감지 시 캐릭터 자동 숨기기
- 전체 화면 종료 시 캐릭터 다시 표시
- 이 기능을 설정에서 끄거나 켜기

Windows에서 안정적으로 감지할 수 있는 공식 또는 검증된 방법을 사용한다.

불필요한 키보드 감시, 화면 녹화, 사용자의 작업 내용 수집은 하지 않는다.

전체 화면 감지가 정확하지 않거나 권한 문제가 있다면 자동 감지 대신 수동 숨기기 기능을 우선 제공한다.

### 11.3 방해 금지 모드

별도의 방해 금지 모드를 제공한다.

- 수동 켜기/끄기
- 특정 시간대 자동 활성화
- 집중 타이머와 연동
- 캐릭터 말풍선 끄기
- 앱 내부 알림 제한
- 필수 타이머 종료 알림은 별도로 설정

이 기능이 다른 Windows 앱의 알림까지 모두 차단한다고 잘못 안내하지 않는다.

시스템 전체 방해 금지와의 연동은 실제 지원되는 방법이 확인된 경우에만 추가한다.

## 12. 기능 I — 아침 브리핑

사용자가 컴퓨터를 켜고 프로그램을 처음 실행하면 그날의 일정과 계획을 귀엽게 안내하는 기능이다.

### 12.1 브리핑 내용

- 오늘 날짜 및 요일
- 오늘의 일정 수
- 오늘 해야 할 일
- 가장 가까운 예정 일정
- 중요한 마감 일정
- 예정된 공부 일정
- 필요하면 전날 미완료 작업 안내

예시:

"좋은 아침! 오늘은 알고리즘 공부랑 팀 회의가 있어."

"오후 2시에 회의가 있으니까 잊지 말자!"

### 12.2 브리핑 방식

- 캐릭터 말풍선
- 작은 브리핑 카드
- 자세히 보기 버튼
- 오늘의 계획 화면으로 이동
- 닫기 버튼

사용자가 긴 브리핑을 원하지 않으면 짧게 보여준다.

### 12.3 설정

- 브리핑 켜기/끄기
- 브리핑 시간 설정
- 컴퓨터 실행 시 표시 여부
- 앱 최초 실행 시 표시 여부
- 간단한 브리핑/상세 브리핑 선택

같은 날 브리핑을 여러 번 반복해서 띄우지 않는다.

브리핑을 놓친 날이 있다고 다음날 과거 브리핑을 연속으로 보여주지 않는다.

시간 판단은 시스템의 지역 시간대를 사용하되, 내부 계산과 저장에 시간대 정보를 명확하게 처리한다.

## 13. 기능 J — 공부 통계

사용자가 실제로 집중한 시간과 학습 패턴을 보기 쉽게 시각화한다.

보상 시스템이 아니라 실제 기록 확인 기능이다.

### 13.1 필수 통계

- 오늘 공부 시간
- 이번 주 공부 시간
- 이번 달 공부 시간
- 전체 누적 공부 시간
- 일별 공부 시간
- 주별 공부 시간
- 월별 공부 시간
- 과목별 공부 시간
- 완료한 집중 세션 수
- 평균 집중 시간
- 최근 공부한 날짜

### 13.2 그래프

최소 다음 시각화를 지원한다.

- 최근 7일 막대그래프
- 최근 30일 공부 시간 그래프
- 과목별 공부 시간 비교
- 월간 캘린더에 공부한 날짜 표시

차트는 보기 쉽고 깔끔하게 구성한다.

데이터가 없는 날은 0으로 올바르게 처리한다.

### 13.3 공부 통계의 정확성

실제 집중한 시간만 집계한다.

다음 사항을 처리한다.

- 중지된 세션
- 일시정지한 세션
- 자정을 넘긴 세션
- 앱 강제 종료
- 시스템 절전
- 날짜 변경
- 데이터 중복 저장

세션이 자정을 넘기면 가능한 한 실제 날짜별로 공부 시간을 분리하여 집계한다.

기록을 삭제하거나 수정하면 관련 통계도 일관되게 변경되어야 한다.

### 13.4 통계와 캐릭터 연동

최근 공부량이 많다면 캐릭터가 짧게 칭찬할 수 있다.

최근 공부가 없으면 앞에서 정의한 감정 규칙을 따른다.

포인트, 경험치, 레벨, 아이템 해금, 연속 출석 보상, 랭킹은 구현하지 않는다.

## 14. 기능 K — 캐릭터 꾸미기 및 교체

캐릭터를 쉽게 바꿀 수 있는 시스템을 구현한다.

### 14.1 캐릭터 선택

초기에는 하나의 기본 캐릭터를 제공한다.

추후 사용자가 이미지 파일을 직접 추가하면 여러 캐릭터 중에서 선택할 수 있어야 한다.

예시:

- 치이카와 이미지 세트
- 하치와레 이미지 세트
- 우사기 이미지 세트
- 사용자가 제작한 오리지널 캐릭터

프로그램이 해당 이미지들을 기본 제공할 필요는 없다.

### 14.2 꾸미기 설정

- 캐릭터 크기
- 기본 표시 위치
- 애니메이션 속도
- 움직임의 빈도
- 말풍선 디자인
- 말풍선 크기
- 캐릭터별 표시 이름
- 배경 소품
- 테마 색상
- 효과음 켜기/끄기
- 캐릭터 이미지 미리 보기

초기에는 UI에서 쉽게 바꿀 수 있는 항목부터 구현하고, 복잡한 의상 합성 기능은 필수 기능 안정화 후 추가한다.

### 14.3 커스텀 이미지 가져오기

사용자가 폴더나 파일을 선택하면 프로그램 내부로 복사하여 관리한다.

- 파일 형식 검사
- 이미지 크기 검사
- 투명도 지원
- 프레임 순서 검사
- 깨진 이미지 예외 처리
- 상태별 이미지 등록
- 애니메이션 미리 보기
- 이미지 누락 시 기본 상태 사용
- 캐릭터 세트 삭제 및 변경

캐릭터 이미지를 프로젝트 설치 폴더에만 저장하지 않는다.

EXE 업데이트나 재설치 후에도 사용자 이미지와 설정이 유지되어야 한다.

## 15. 기능 L — Planit 앱 연계

사용자는 기존에 사용하던 Planit 앱의 일정과 이 프로그램의 캘린더를 가능한 한 연동하고 싶어 한다.

우선 연동 대상으로 '플래닛 - 할 일, 일정, 캘린더' (Planit KR)를 가정한다.

하지만 Planit이라는 이름을 사용하는 다른 앱도 있으므로 최종 서비스 식별은 별도로 확인 가능해야 한다.

### 15.1 중요한 전제

공식적으로 지원되는 API, 캘린더 구독 URL, 외부 파일 내보내기 및 가져오기 방법이 실제로 존재하는지 먼저 조사하고 검증한다.

확인되지 않은 API를 만들어서 구현하지 않는다.

비공식 서버 주소를 추측하거나, 모바일 앱을 역공학하여 인증정보를 추출하거나, 사용자 계정 비밀번호를 수집하지 않는다.

### 15.2 연동 방식 우선순위

**1순위 — 공식 API 연동**

공식 문서와 허용된 인증 방식이 있다면 API 연동을 구현한다.

가능한 경우:

- 일정 가져오기
- 일정 내보내기
- 동기화 상태 확인
- 충돌 처리
- 수동 동기화
- 사용자 승인 후 자동 동기화

**2순위 — 공식 캘린더 내보내기 또는 구독**

Planit이 공식적으로 ICS 파일, 캘린더 URL 등의 방법을 지원한다면 해당 방식을 활용한다.

읽기 전용 구독과 양방향 동기화를 구분한다.

**3순위 — 수동 파일 연동**

Planit과 직접 연계가 불가능하다면 Desktop Buddy 자체에서 표준 ICS 가져오기/내보내기 기능을 제공한다.

다만 Planit에서도 해당 형식을 지원하는 경우에만 양쪽 사이의 수동 데이터 교환이 가능하다고 안내한다.

### 15.3 연동 인터페이스 설계

다음과 같이 외부 캘린더 제공자를 교체하기 쉬운 구조로 설계한다.

- LocalCalendarProvider
- ICSFileProvider
- PlanitProvider (공식 지원 확인 전에는 비활성화)

공식 연동 방법이 아직 없더라도 앱 자체 캘린더는 완전히 정상 동작해야 한다.

설정 화면에는 다음 상태를 구분한다.

- 로컬 캘린더 사용 중
- 파일 가져오기/내보내기 가능
- 외부 캘린더 연결됨
- 연결 필요
- 연동 미지원 또는 공식 지원 확인 필요

실제로 구현되지 않은 연동을 "연결됨" 또는 "동기화 완료"라고 표시하면 안 된다.

### 15.4 데이터 동기화 원칙

- 같은 일정이 중복 생성되지 않도록 외부 ID를 저장
- 원본 데이터 출처 기록
- 수정된 시각 기록
- 동기화 충돌 처리
- 데이터 삭제 전 확인
- 내보내기 전에 미리 보기
- 사용자 명시적 동의 없이 외부 앱 데이터를 덮어쓰지 않기

초기에는 안정적인 로컬 캘린더 기능을 우선 완성한다.

설정 변경 사항은 즉시 반영하거나 저장 버튼을 통해 명확하게 반영한다.

## 17. UI/UX 디자인 요구사항

전체적인 디자인은 귀엽지만 어린아이용 장난감처럼 보이지 않는, 깔끔하고 세련된 생산성 앱을 목표로 한다.

### 17.1 디자인 방향

- 부드러운 파스텔 색상
- 따뜻한 느낌의 배경색
- 둥근 모서리
- 심플한 아이콘
- 충분한 여백
- 읽기 편한 한국어 글꼴
- 작은 애니메이션과 자연스러운 전환
- 복잡하지 않은 설정 화면
- 밝은 모드와 어두운 모드

Windows에서 안정적으로 표시되는 기본 시스템 폰트를 우선 사용한다.

### 17.2 통합 관리창 레이아웃

권장 레이아웃:

왼쪽: 기능 메뉴  
오른쪽: 현재 선택한 기능 화면

메뉴:

홈 / 오늘 / 캘린더 / 집중 / 통계 / 채팅 / 꾸미기 / 설정

앱 크기가 작아지면 메뉴와 콘텐츠가 적절히 축소되어야 한다.

캘린더는 일반적인 앱 창 크기에서 충분히 크게 보여야 한다.

### 17.3 홈 화면

홈 화면에 다음을 배치한다.

- 오늘 날짜
- 캐릭터와 짧은 인사
- 오늘 할 일
- 다음 일정
- 빠른 집중 타이머
- 오늘 공부 시간
- 캘린더 바로가기

한 화면에 모든 세부 설정을 표시하지 않는다.

자주 사용하는 기능을 중심으로 구성한다.

### 17.4 접근성

- 읽기 쉬운 글자 크기
- 충분한 버튼 클릭 영역
- 아이콘만 있는 버튼에는 툴팁
- 키보드로 주요 설정 조작 가능
- 대비가 너무 낮은 텍스트 방지
- 시스템 DPI 변경 대응
- 애니메이션을 줄이거나 끄는 설정

### 17.5 피해야 할 UI

- 과도한 팝업
- 불필요한 모달창
- 항상 떠 있는 커다란 기능 창
- 너무 많은 애니메이션
- 기능마다 다른 스타일
- 지나치게 작은 글씨
- 화면 밖으로 사라지는 메뉴
- 저장 버튼이 어디에 있는지 알 수 없는 UI
- 무조건 API 키부터 입력하라는 화면

### 18.3 저장 위치

예시:

%LOCALAPPDATA%/DesktopBuddy/

설치 폴더에 DB를 저장하지 않는다.

EXE 파일을 업데이트해도 DB가 유지되어야 한다.

### 18.4 데이터 안전성

- SQLite 트랜잭션 활용
- 데이터베이스 스키마 버전 관리
- 필요할 때 마이그레이션
- 마이그레이션 전 백업
- 잘못된 데이터에 대한 예외 처리
- 중복 기록 방지
- 정상 종료 및 강제 종료 대비
- 불필요한 민감정보 저장 최소화

개발 중 오류가 발생했다고 사용자 DB를 임의로 삭제하거나 초기화하지 않는다.

필요하지 않은 디렉터리는 억지로 만들지 않아도 된다.

각 폴더의 역할을 명확히 한다.

특히 다음 기능은 UI 코드와 비즈니스 로직을 분리해야 한다.

- 타이머
- 일정 관리

- 감정 상태 계산

따라서 타이머를 독립 서비스로 만들고, UI와 채팅 기능이 동일한 서비스를 호출하도록 설계한다.

### 19.1 캐릭터 상태 관리

캐릭터 애니메이션은 이벤트 기반 상태 관리자 또는 상태 머신으로 구현한다.

각 기능이 직접 캐릭터 이미지를 강제로 변경하는 코드가 여기저기 흩어지지 않게 한다.

### 19.2 서비스 계층

UI에서 데이터베이스 SQL을 직접 호출하는 방식은 최소화한다.

서비스 계층을 통해 일정 조회, 할 일 완료, 타이머 시작 등의 기능을 실행한다.

### 19.3 확장 가능성

추후 다음 기능을 추가하기 쉽게 한다.

- 새로운 캐릭터
- 새로운 AI 제공자
- 다른 캘린더 제공자
- 새로운 통계
- 추가 알림 방식

다만 미래 확장만 고려한 과도한 추상화는 피한다.

## 20. 성능 및 Windows 안정성

데스크톱 펫은 장시간 실행되므로 다음 사항을 중요하게 다룬다.

- 실행 중 CPU 점유율 최소화
- 불필요한 이미지 재로딩 방지
- 숨겨진 창의 애니메이션 일시 중단
- 과도한 폴링 방지
- 타이머 정확성 유지
- 네트워크 요청으로 GUI 멈춤 방지
- 메인 스레드에서 오래 걸리는 작업 실행 금지
- 데이터베이스 오류 발생 시 앱 전체 종료 방지
- 여러 모니터 대응
- DPI 변경 대응
- Windows 절전/복귀 대응
- 중복 실행 방지
- 정상 종료 시 데이터 저장
- 트레이 아이콘이 사라지는 문제 방지

특히 프로그램이 작은 캐릭터 하나만 보여주고 있을 때 시스템 자원을 많이 사용해서는 안 된다.

항상 위에 표시되는 창이 게임이나 전체 화면 동영상 위에서 방해되지 않도록 한다.

앱이 완전히 종료된 상태와 트레이에서 백그라운드 실행 중인 상태를 명확하게 구분한다.

## 22. Windows 설치 및 EXE 배포

최종적으로 Python이나 VS Code를 설치하지 않은 일반 사용자도 실행할 수 있는 Windows 앱을 만들고 싶다.

### 22.1 개발용 실행

다음 파일을 제공한다.

- setup_windows.bat
- run_windows.bat
- build_windows.bat

Windows 초보자가 파일을 더블클릭하여 실행할 수 있도록 한다.

오류가 발생하면 창이 즉시 닫혀 원인을 확인할 수 없게 하지 않는다.

### 22.2 EXE 패키징

PyInstaller를 사용한다.

초기에는 디버깅이 쉬운 one-folder 배포를 우선한다.

안정화 후 단일 EXE 방식이나 설치 프로그램을 검토한다.

필수 고려사항:

- 캐릭터 에셋 포함
- Qt 플러그인 포함
- 데이터 저장 경로 분리
- 실행 아이콘
- 앱 버전
- Windows 실행 테스트
- 사용자 설정 유지
- 프로그램 재실행
- 오류 로그 확인
- 설치 없이 실행하는 방식과 설치형 방식의 차이 문서화

### 22.3 최종 사용 흐름

일반 사용자는 다음과 같이 이용할 수 있어야 한다.

1. 배포 파일 다운로드
2. 압축 해제 또는 설치
3. 실행
4. 캐릭터 표시
5. 더블클릭으로 관리창 열기
6. 즉시 일정 및 타이머 사용

AI 기능이 필요하지 않으면 그 이상의 설정이 없어야 한다.

## 24. 반드시 수행할 테스트

각 기능마다 정상 동작, 예외 상황, 데이터 저장을 테스트한다.

최소 다음 사례를 검증한다.

### 캐릭터

1. 캐릭터가 투명한 배경으로 표시된다.
2. 드래그 후 위치가 저장된다.
3. 더블클릭 시 관리창이 한 번만 열린다.
4. 단일 클릭 반응이 더블클릭과 충돌하지 않는다.
5. 모니터 해상도를 바꿔도 캐릭터를 다시 찾을 수 있다.
6. 트레이 숨기기/복원/종료가 정상 작동한다.

### 계획 및 달력

7. 할 일이 등록되고 재실행 후 유지된다.
8. 완료 상태가 정확히 저장된다.
9. 반복 일정이 지정 요일에 나타난다.
10. 특정 반복 일정 하나만 수정할 수 있다.
11. 하루를 넘는 일정도 올바르게 표시된다.
12. 중복 일정 및 중복 알림이 발생하지 않는다.

### 타이머

13. 25분 타이머가 정확하게 진행된다.
14. 일시정지 시간이 집중 시간에 포함되지 않는다.
15. 중간 종료한 세션이 완료로 기록되지 않는다.
16. 앱 재실행 시 잘못된 집중 시간이 생성되지 않는다.
17. 자정을 넘긴 집중 기록이 올바르게 집계된다.

### 감정

18. 처음 실행했을 때 기록이 없다는 이유로 슬퍼하지 않는다.
19. 설정한 공부 공백 기준일 이후 슬픈 상태가 적용된다.
20. 유효한 공부 세션이 완료되면 상태가 갱신된다.
21. 휴식일 제외 설정이 적용된다.
22. 감정 기능을 끄면 슬픔 상태가 강제로 적용되지 않는다.

### 채팅 및 AI

23. API 키 없이 앱이 정상 실행된다.
24. 오프라인 명령으로 타이머가 시작된다.
25. AI 연결 실패가 다른 기능을 중단시키지 않는다.
26. 데이터 삭제 명령은 사용자 확인을 거친다.
27. API 키가 로그나 설정 파일에 노출되지 않는다.

### 전체 안정성

28. 앱 재실행 후 주요 데이터가 보존된다.
29. 중복 실행 시 창과 트레이 아이콘이 여러 개 생기지 않는다.
30. 앱 종료 시 불필요한 프로세스가 남지 않는다.
31. 시스템 절전 복귀 이후 타이머와 알림이 오작동하지 않는다.
32. EXE 패키징 후에도 리소스와 DB 경로가 정상이다.

GUI와 Windows 전용 기능을 현재 실행 환경에서 직접 테스트할 수 없다면, 테스트를 완료했다고 주장하지 마라.

자동 테스트 결과와 실제 사용자 PC에서 확인해야 할 수동 테스트를 구분하여 보고한다.

## 25. Codex의 실제 작업 방식

개발을 다음 규칙으로 수행하라.

### 25.1 새 프로젝트에서 시작

현재 프로젝트 폴더가 비어 있다면 처음부터 필요한 파일을 생성한다.

이전에 사용했던 다른 프로젝트나 ZIP 파일이 있다고 가정하지 않는다.

기존 코드를 찾기 위해 불필요하게 다른 폴더를 검색하지 않는다.

### 25.2 실제 코드 작성

단순히 다음과 같은 답변만 하면 안 된다.

"이런 방식으로 구현하면 됩니다."

반드시 실제 코드를 작성하고 프로젝트 파일을 수정한다.

단, 대규모 작업은 단계별로 수행한다.

### 25.3 단계별 완료 원칙

각 단계에서 다음을 수행한다.

1. 현재 단계의 목표 확인
2. 관련 파일 및 기존 코드 분석
3. 구현 계획
4. 실제 코드 작성
5. 자동 테스트 작성
6. 실행 가능한 범위에서 테스트
7. 오류 수정
8. 코드 정리
9. 문서 업데이트
10. 완료 결과 보고

현재 단계 밖의 기능을 무리하게 구현하지 않는다.

### 25.4 새로운 기능을 구현할 때

기존 데이터 구조와 호환성을 확인한다.

필요하면 DB 마이그레이션을 작성한다.

기존 데이터를 임의로 삭제하지 않는다.

기존 기능의 회귀 테스트를 수행한다.

### 25.5 오류가 발생했을 때

오류 메시지를 읽고 원인을 분석한다.

가능한 경우 스스로 수정하고 다시 테스트한다.

같은 오류가 반복되는 경우 무작정 코드를 복잡하게 만들지 말고 근본 원인을 찾는다.

내가 오류 메시지나 스크린샷을 보내면 해당 문제부터 해결한다.

### 25.6 나에게 보고할 내용

각 작업 완료 후 한국어로 다음 항목을 알려라.

- 이번에 구현한 기능
- 실제 변경한 주요 파일
- 실행한 테스트와 결과
- 아직 검증하지 못한 사항
- Windows에서 실행하는 방법
- 내가 직접 확인할 동작
- 다음 개발 단계

코드 수정 없이 설명만 제공한 경우에는 그 사실을 명확히 말한다.

## 26. 완성도 기준

기능이 있다는 사실만으로 완료로 판단하지 않는다.

다음 조건을 충족해야 완료로 인정한다.

### 기본 기능 품질

- 실제 사용자 조작이 가능
- 버튼이 정상 작동
- 입력값이 저장됨
- 창을 닫았다 열어도 상태 유지
- 오류 발생 시 앱 전체 종료 방지
- 화면 표시가 깨지지 않음

### 사용자 경험

- 초보자가 기능을 찾기 쉬움
- 클릭 횟수가 불필요하게 많지 않음
- 설정이 일관됨
- 복잡한 기술 용어가 사용자에게 노출되지 않음
- API 키 없이도 사용할 수 있음

### 개발 품질

- 모듈 구조가 명확함
- 예외 처리가 되어 있음
- 코드 중복이 적음
- 테스트 가능함
- README가 최신 상태임
- 기능 변경 시 다른 기능이 망가지지 않음

### 최종 목표

Python이나 개발 도구를 모르는 일반 사용자가 Windows에서 프로그램을 실행하고, 캐릭터를 더블클릭하여 필요한 기능을 편리하게 사용할 수 있는 수준을 목표로 한다.
