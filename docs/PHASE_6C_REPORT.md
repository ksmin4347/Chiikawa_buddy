# PHASE 6C 검토 — 0.6.2

2026-11-11 후속 요청에 따라 제한된 AI 작업 제안·확인 카드를 구현했습니다. 실제 사용자 키/DB나 실제 API를 사용하지 않았습니다. 변경 범위와 실행 증거를 아래에 구분합니다.

## 구현

- `ai/proposals.py`: strict 함수 4종의 명세와 독립 인수 검증. 할 일/일정 추가, 날짜 이동/완료/완료 취소/삭제, 타이머 5종 제어, 기기 내 일정/공부/상태 조회. 알 수 없는 이름·추가/누락/중복 키·잘못된 정확한 타입·형식/의미·범위를 거부합니다. 인수 최대 4,096자, 제목 1~200자, 날짜 1900~2100, 시각 HH:MM, 시작 분 1~1,440. 모델은 승인/카드 ID/DB ID/반복 범위를 지정할 수 없습니다.
- `ai/client.py`: 별도 허용된 chat 요청만 함수 명세와 기준 서울 날짜를 전송. `parallel_tool_calls=false`, 단일 응답의 함수 최대 하나. 인수의 실제 키·비밀 패턴은 작업 스레드에서 검사하고 잘못된 제안은 정적 오류로 바꿉니다. 함수 제안과 함께 온 모델의 완료/승인 주장은 버립니다. SQL·파일·셸·외부 도구·자동 후속 HTTP가 없습니다.
- `OnlineService`: 실행 중에만 유지하는 별도 허용, 요청 당시 기준 날짜/캐릭터/맥락과 연결. 허용 끄기·맥락 전환·화면/창 닫기·종료 후 카드/지연 결과를 무효화합니다. 대기 중 날짜가 바뀌어도 제안을 버립니다.
- `ChatService`/`Pending`/`CommandExecutor`: 앱이 발급한 확인·선택·만료·현재 대상/타이머 fingerprint·중복 receipt·트랜잭션 롤백 재사용. 모든 AI 변경은 확인 후 적용합니다. 동명 대상·반복 범위 선택 뒤에도 AI 출처를 보존합니다. 조회는 실제 앱 결과를 기기 안에만 표시합니다. DB 스키마 6과 기존 mode/화자를 유지하며 과거 대화/원본 사진을 바꾸지 않았습니다.
- `ChatPage`: 별도 허용 체크박스와 읽기 전용 제안 상세·출처, 기존 키보드 확인/취소. 작은 창에서 제안 도착 시 상세와 확인 버튼을 먼저 보여줍니다. 일반 AI 문장은 실행 권한이 없으며 앱의 저장/타이머 결과만 완료로 표시합니다.

함수 명세의 strict/필수 nullable/닫힌 객체·병렬 호출 금지는 [OpenAI 공식 함수 호출 문서](https://developers.openai.com/api/docs/guides/function-calling)를 확인했습니다. 실제 계정별 모델 지원을 확인한 것은 아닙니다. 구현은 왕복 한 번이며 조회 결과/DB 목록을 모델에 반환하지 않습니다. 이전 대화·DB 결과의 선택적 전송 동의, 새 반복 생성·일반 제목/시간 편집·일괄 변경은 제공하지 않습니다.

처음 신규 검사에서 잘못 사용한 시험 시계 필드/반복 인수명/화면 상수와 대화 보관 검사의 DB 조회 범위를 고쳤습니다. 앱 데이터를 삭제하거나 기능 동작을 그 검사에 맞춰 바꾸지 않았습니다. 이후 신규 100개를 통과했습니다.

화면 자동 배치 검사만으로 놓친 문제가 있었습니다. 제안 도착 시 입력창으로 이동해 카드가 위에 가려져, 최소 창에서도 상세/확인 버튼 쪽으로 이동하도록 고쳤습니다. 실제 viewport 안의 출처와 확인 버튼 위치를 회귀로 검사하고 4배율 화면을 다시 렌더링했습니다. 긴 상세는 읽기 전용 입력 안에서 스크롤/복사합니다. 이미지 예시는 앱 위젯과 QA 데이터만 사용했습니다.

Windows 검사 실행 순서에서 기존 로그 차단 검사가 가짜 canary를 캡처했습니다. 상위 로거의 전파 차단만 사용하는 대신 현재 존재하는 SDK/HTTP 자식 로거까지 직접 비활성화하고 SDK import 전·후에 적용했습니다. 직접 연결한 로그 핸들러를 포함해 검사했습니다. 실제 키는 사용하지 않았습니다. 전체 회귀 후 이 보강에 관련된 클라이언트/온라인/Windows Qt 검사를 다시 실행했으며 빌드도 다시 만들었습니다.

추가 검토에서 JSON 이스케이프로 감춘 인수도 디코딩 후 검사하도록 보강했습니다. 원시 인수의 키 패턴뿐 아니라 변환한 문자열의 패턴과 실제 저장된 가짜 키의 일치를 작업 스레드에서 검사합니다. 일반/이스케이프 canary 두 경우와 인수 거부 관련 36개를 먼저 확인하고, 마지막 전체 회귀와 Windows 관련 검사·빌드에 포함했습니다.

HTTP는 `httpx2.MockTransport`, 키는 메모리 대체 저장소, GUI DB는 고유 QA 경로만 사용했습니다. literal SQL/HTML/승인 문구는 제목 데이터로 취급하고, 승인 필드·허용하지 않은 함수·복수 호출·비밀 값은 거부했습니다. 타이머 5종은 확인 전 상태 불변, 중복/롤백/만료/대상 변경·키/모드/페이지 등 10종 맥락 변경·자정 경계·기기 내 조회의 HTTP 추가 전송 없음을 확인했습니다.
